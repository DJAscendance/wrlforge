# CLAUDE.md

This project is **WRL Forge** (formerly `vrmlpad`). See `AGENTS.md` for the full mission (including the three-profile model: Mall Item, World Project, Generic VRML97), architecture, conventions, and known gotchas — it applies equally here. See `docs/WRL_FORGE_ROADMAP.md` for the phased build-out plan and which phase is currently active.

A couple of Claude-specific notes on top of that:

- This is a tool-building project, not an item-authoring one. Don't pull in `../new-items/CLAUDE.md` conventions about VRML content itself (forbidden nodes, placement, etc.) except insofar as the Mall Item `validator.js` needs to check for them — this repo's job is the tool, not the mall items. Those conventions are Mall Item-specific; do not assume they apply to World Project or Generic VRML97 code.
- Before adding any dependency (editor component, 3D lib, UI framework), re-read the "Mission" section in `AGENTS.md`. Root runtime deps are deliberately minimal: `x_ite` (MIT) is the only `dependency`; `electron` and `electron-builder` (MIT, Phase 6A Windows build tooling) are `devDependencies`. Do **not** add a third-party archive library — the World Project Bundle ZIP uses Node's built-in `zlib` (`src/world-project/zip-writer.js`). The **optional** external editor is discovered cross-platform via `src/editor/editor-locator.js` (Linux `codium`/`code`, Windows install-location search + `WRL_FORGE_EDITOR`/`settings.json` override, clear not-found message); don't reintroduce a hardcoded `codium` spawn. VSCodium is optional, not required. The **VRML97 parser** foundation is now **built** (Phase 7A): a dependency-free, token-driven tokenizer + structural parser under `src/vrml/` (`tokenizer`/`parser`/`ast`/`diagnostics`/`analyze`/`asset-refs`/`index`; see `docs/VRML_PARSER.md`). It is pure (text in, tree + diagnostics + semantic index + asset-refs out — no fs/Electron), profile-neutral, ships **alongside** the existing systems, and is **not** wired into any production path — do not route `validator.js`/World scanning/preview/packaging through it without a new approved lane. 7A1 corpus-hardened it (hyphen/plus identifiers, multiline strings, header encoding case, lenient Cybertown/Blaxxun `ROUTE`/`PROTO`-in-MFNode-array; 98.1% corpus diagnostic reduction). Its **semantic scope is flat and NOT authoritative** (PROTO DEF leakage, cross-PROTO false duplicate-`DEF`, USE-before-DEF, context-insensitive `IS`) — a future scope-aware lane fixes that; do not surface those `DEF`/`USE`/`ROUTE` diagnostics as authoritative, and do not attempt the PROTO-scope rewrite here. Reuse it (`require('./src/vrml')`), don't fork it. The **native editor** on top of it (Phase 7B, `docs/NATIVE_EDITOR_ARCHITECTURE.md`) is still a PLAN — do not build the editor UI, replace production validators, or add an unsaved-buffer preview without a separately approved lane; and do **not** build a renderer (X_ITE only). Direct upload/auth/networking **will not be built** (locked product decision); do not present its absence as a missing feature. Windows build instructions are in `docs/BUILD.md`; artifacts are labelled "Private Beta — Unsigned" (no signing/auto-update/store/public release). The Mall Item lane (Phase 2B1) **and** the World Project lane (Phase 4B) now have embedded X_ITE previews (`x_ite` MIT is a root dependency; see `docs/PREVIEW_ARCHITECTURE.md`), but that is **not** a license to add rendering dependencies opportunistically: X_ITE is the only approved renderer, and the Generic VRML97 embedded preview (Phase 5) still needs its own approved lane. Do not build a custom VRML/X3D renderer. Shared preview/fit modules live in `src/preview/` — reuse them, don't duplicate. The World preview is a **separate profile** (`renderer/world-preview.js`, `src/world-project/preview-source.js`): it reuses the shared gzip reader but applies **no** Mall fit/guide/placement/cap rules.
- Don't rename internal symbols (IPC channel names, the `window.vrmlpad` bridge, variable names) purely for branding consistency with the new product name. `AGENTS.md` explains which ones were intentionally kept during the rename and why. The World Project lane (Phase 4A) deliberately reuses the `window.vrmlpad` bridge (adding a `world` sub-object) rather than introducing a new bridge name.
- The **World Project** lane lives in `src/world-project/` (production, read-only resolver + Phase 4B `preview-source` + Phase 5A `package-plan`/`zip-writer`/`bundle-builder`), `renderer/world.html` + `world.js` + `world-preview.js` + `world-packaging.js` (its own workspace page, with an embedded X_ITE preview and a packaging section), and confined `world:*` IPC in `main.js` (incl. `world:previewLoad` + the `wrlworld://` scheme handler, and `world:packageAudit` + `world:buildReviewBundle`). It is a **separate profile** from Mall Item — never apply `validator.js`/Mall rules to it, and never encode a fixed texture limit (the ~20 figure is disproven; worlds reach ~70). It is read-only except the **one** explicit Build-World-Project-Bundle action (IPC channel `world:buildReviewBundle` — an internal name kept for stability, do not rename), which writes only a portable ZIP to a caller-chosen destination **outside** the project (never repair/copy/rename/delete/upload; never mutate the source). The Phase 4B preview only reads and is **analysis + display only**; the Phase 5A packaging is a **review + manual hand-off bundle** — labelled “WRL Forge World Project Bundle”, uploaded by hand through the Cybertown website, no direct upload (which will not be built), no server-certified-format claim (open questions in `docs/WORLD_PACKAGE_QUESTIONS.md`). The bundle uses a deterministic in-repo ZIP writer built on Node `zlib` only — **do not add a third-party archive dependency**. The world preview authorizes X_ITE's nested reads from the asset graph via the `wrlworld://` scheme (confined to project root, gzip-decompressed) — do not let X_ITE reach `file://` or the network directly, and do not create `.edit.wrl` files to preview a world. `qa/world-recon/*` re-export the production modules; don't duplicate them. Any Electron visual work still routes through `VisualQaRunner` (`qa/phase-4b-world-preview/` and `qa/phase-5a-world-packaging/` are the world runs). See `docs/WORLD_PROJECT_ARCHITECTURE.md` and `docs/PREVIEW_ARCHITECTURE.md`.

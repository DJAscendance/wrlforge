**Classification: `STALE_STATE_REPORTING`** (expected race between WRL Forge
overlay state and X_ITE's internal render pipeline). No product fix is
required for this lane.

## 16. Tier-3 BOM root cause + correction

**Cause:** PowerShell's `Out-File -Encoding utf8` (the default Tier-3 smoke
generator) writes UTF-8 **with BOM** (PS 5.1 quirk). The prior code path in
both `qa/visual-qa/cli.js:109` and `main.js:718` was `JSON.parse(fs.readFileSync
(file, 'utf8'))`, which rejects a leading U+FEFF with `SyntaxError: Unexpected
token`. Net effect from the harness' perspective: the CLI rejected the jobs
file before launching the server ("READY never arrived"); even when the server
did launch, it emitted READY then immediately `WRL_FORGE_CAPTURE_ERR
- bad-jobs-file`.

**Correction:** narrow BOM-tolerant reader. New module
`qa/visual-qa/json-file.js` exports `readJsonFile(path)` which strips one
leading U+FEFF before parsing. `qa/visual-qa/cli.js` and
`qa/phase-7c-windows/orchestrate.js` now use it. `main.js` capture-server
(the test-only reader in the packaged binary) now does the same inline strip.
Regression test `test/visual-qa/json-file.test.js` proves BOM-free input,
BOM-prefixed input (the PowerShell case), plain `JSON.parse` rejection of a
BOM file (the old failure), and that a non-JSON body still throws. **4/4
pass.**

The portable-EXE finding was the same root cause: the capture-server never
made it past `JSON.parse` on the BOM-prefixed jobs file before the runner
timed out. After the fix, `WRL_FORGE_CAPTURE_READY` is reached and
`WRL_FORGE_CAPTURE_OK` is emitted.

## 17. Lockfile + version-edit procedure

**Finding:** the prior `npm install --no-audit --no-fund` on the Windows clone
regenerated `package-lock.json` with two differences from the committed
file: (a) root `version` field bumped from `1.3.0-beta.3` to `1.3.0-beta.5`
(an npm auto-edit when the workspace's `package.json` changes), (b) LF→CRLF
line endings (Windows Node + npm). The dependency graph itself was **unchanged**
(same 374 packages, same `lockfileVersion: 3`).

**Classification:** `LOCKFILE_NON_MATERIAL`. No dependency change. No
graph change.

**Future minimal version-edit procedure:**

1. Update `package.json` `version` field on the working tree.
2. Do **not** run `npm install`. Use `npm ci` (uses the existing lockfile
   verbatim, does not modify it) only if node_modules is missing.
3. If `npm install` must be run (e.g. node_modules was wiped), expect the
   lockfile to drift and treat it as cosmetic; never commit the drift.
4. The committed `package-lock.json` is left at its historical version
   (`1.3.0-beta.3` root metadata); the actual install graph is what `npm ci`
   restores.
